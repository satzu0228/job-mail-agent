# 求职邮件智能管理系统 MVP 范围与验收基线

> 状态：MVP 业务范围已冻结
> 版本：v1.1
> 冻结日期：2026-07-27
> 适用阶段：第二阶段至首个端到端版本验收
> 变更原则：业务范围变更必须记录原因、收益、代价以及对数据库、API、测试和论文的影响

## 1. 冻结目的

本文件规定毕业设计首个可演示版本必须完成的业务闭环、功能边界和验收标准。后续架构、数据库、接口、前端和测试设计均以本文件为范围基线。

本次冻结的是“用户能够完成什么”和“怎样算完成”，不锁死以下实现细节：

- 四个核心 Agent 的内部实现形式；
- LangGraph checkpoint 的具体存储实现；
- 后台任务框架；
- DeepSeek/Qwen 的主备选择；
- Vue 与工作流进度采用轮询、SSE 还是 WebSocket。

这些内容通过后续架构决策确定，但不能削弱本文件规定的人工审核、幂等、审计和数据隔离要求。

## 2. MVP 目标用户与运行边界

### 2.1 目标用户

MVP 面向集中求职期间需要处理招聘邮件的个人用户，主要解决：

- 求职邮件容易混在普通邮件中；
- 面试、笔试和材料截止时间容易遗漏；
- 同一公司、不同岗位的申请进度难以追踪；
- 回复邮件需要反复整理上下文；
- 模型自动处理结果需要人工确认。

### 2.2 首版运行边界

- 采用单用户演示模式，但核心数据必须保留 `user_id` 或等价资源归属关系。
- 演示时只要求同时添加并启用一个测试邮箱账户，真实端到端验收仍以 163 测试邮箱
  作为稳定基线。
- 邮箱配置提供 163、126、QQ、Gmail 和自定义 IMAP/SMTP 预设，Provider、数据模型
  和业务接口不得写死单一服务商。
- 只同步 `INBOX`，由用户手动触发增量同步。
- 只处理测试邮箱和脱敏/模拟求职邮件，不使用真实个人求职邮箱作为演示数据。
- 系统时间默认按用户配置时区处理；演示默认时区为 `Asia/Shanghai`。

## 3. MVP 唯一主闭环

MVP 必须完整跑通以下纵向场景：

```text
添加 163 测试邮箱
→ 测试连接
→ 手动增量同步 INBOX
→ 查看邮件列表与安全邮件详情
→ 对单封邮件启动 AI 分析
→ 判断求职相关性并分类
→ 抽取公司、岗位、联系人、时间、地点、链接、材料和截止日期
→ 匹配已有申请或提出新建申请建议
→ 提出申请阶段、任务或日程变更建议
→ 按需生成回复草稿
→ 用户审核建议与草稿
→ 执行获批的数据库变更或 SMTP 发送
→ 在求职看板和申请时间线中查看结果
```

闭环中的任一步失败时，系统必须保存可解释的失败状态，不得把未完成操作标记为成功。

## 4. MVP 功能范围

### 4.1 邮箱账户

必须支持：

- 添加一个 163、126、QQ、Gmail 或自定义 IMAP/SMTP 测试邮箱账户；
- 选择预设 Provider 时自动填充 IMAP/SMTP 主机、端口和安全方式；
- 选择自定义 Provider 时允许配置 IMAP/SMTP 主机、端口和安全方式；
- 测试 IMAP、SMTP 连接；
- 启用或停用账户；
- 展示脱敏后的邮箱地址和连接状态；
- 从环境变量或安全凭据机制读取授权码，不在页面、日志或普通业务字段中明文展示。

验收标准：

- 正确配置时，连接测试明确返回 IMAP 和 SMTP 的独立结果。
- 授权码错误、超时或服务器拒绝时，返回可理解的错误且不泄露凭据。
- API 响应、日志和错误信息中不出现完整授权码。
- Gmail 仅验收应用专用密码方式，不把普通账户密码或“使用 Google 登录”描述为
  已支持能力。
- Outlook.com 和 Microsoft 365 在实现 OAuth2/XOAUTH2 前不得出现在“已支持”
  Provider 列表中。

### 4.2 邮件手动增量同步

必须支持：

- 用户手动触发 `INBOX` 同步；
- 按账户、文件夹、`UIDVALIDITY` 和 UID 增量获取邮件；
- 保存 `Message-ID` 作为辅助去重信息；
- 解析主题、发件人、收件人、时间、纯文本和 HTML 正文；
- 对 HTML 进行安全清洗后再展示；
- 保存附件元数据；不持久化或智能解析附件内容，并限制大附件获取；
- 展示本次新增、跳过、失败的邮件数量。

验收标准：

- 同一批邮件连续同步两次，不产生重复邮件记录。
- 同步过程中不主动把未读邮件标成已读。
- 中文主题、地址显示名和正文可以正常解析。
- HTML 中的脚本、事件属性和远程跟踪资源不会被前端直接执行或加载。
- 单封邮件解析失败不导致整批同步结果回滚或被错误标记为全部成功。

### 4.3 邮件列表与详情

必须支持：

- 查看邮件列表；
- 按求职相关性、邮件类别和处理状态筛选；
- 查看主题、参与者、时间、安全正文和附件元数据；
- 查看 AI 分类、结构化抽取、置信度、证据和处理状态；
- 对尚未分析或分析失败的邮件重新发起分析。

验收标准：

- 用户只能读取属于自己的邮箱账户和邮件。
- 邮件详情明确区分原始邮件事实、模型建议和用户确认结果。
- 分析失败或低置信度时展示原因，不静默填充猜测值。

### 4.4 求职邮件分类

顶层分类冻结为：

```text
INTERVIEW
ASSESSMENT
OFFER
REJECTION
MATERIAL_REQUEST
APPLICATION_UPDATE
RECRUITER_COMMUNICATION
JOB_RELATED_OTHER
NON_JOB
```

分类结果至少包含：

- `is_job_related`
- `category`
- `priority`
- `should_reply`
- `confidence`
- `evidence`
- `schema_version`

“面试改期”“二面通知”“材料截止”等细节由 `event_type` 或结构化事件表达，不扩展为另一套顶层分类。

验收标准：

- 输出必须通过强类型 Schema 和枚举校验后才能进入后续节点。
- Schema 失败、结果冲突或低于配置阈值时进入待确认状态。
- `NON_JOB` 邮件不会自动创建申请、任务或回复草稿。
- 模型解释文字中出现其他类别名称时，不会改变最终结构化分类。

### 4.5 结构化信息抽取

必须支持抽取：

- 公司名称；
- 岗位名称；
- 求职阶段或事件类型；
- 联系人及联系方式；
- 面试或笔试时间；
- 材料截止日期；
- 地点；
- 会议链接；
- 材料要求。

时间字段必须同时保存：

- 原始时间文本；
- 标准化的带时区时间；
- 时区；
- 置信度；
- 来源证据；
- 是否需要人工确认。

验收标准：

- 不存在的字段返回空值和缺失标记，不允许模型自行补全。
- “明天下午”“本周五”等依赖上下文的时间，以邮件日期和用户时区解析并保留原文。
- 年份、日期或时区不明确时，不自动创建已确认日程。
- 会议链接只做格式和协议校验，不自动打开。

### 4.6 求职申请匹配与阶段管理

申请阶段冻结为：

```text
APPLIED
ASSESSMENT
INTERVIEW
OFFER
REJECTED
WITHDRAWN
```

必须支持：

- 根据公司、岗位、联系人、来源邮件和时间范围查询候选申请；
- 输出唯一匹配、多个候选或未匹配；
- 对未匹配邮件提出新建申请建议；
- 对已匹配申请提出阶段变更建议；
- 使用确定性状态机校验阶段迁移；
- 保存来源邮件和申请时间线。

验收标准：

- Agent 只有只读查询权限，不直接创建申请或修改阶段。
- MVP 中，新建申请和阶段变更均需要用户确认后执行。
- 多个候选、同公司多岗位或核心字段冲突时必须由用户选择。
- “面试改期”和“多轮面试”记录为时间线事件，不伪造成重复阶段迁移。
- 模型建议阶段、用户确认阶段和最终执行结果分别保存。

### 4.7 内部任务与日程建议

必须支持：

- 根据面试、笔试和材料截止信息生成内部任务或日程建议；
- 在系统内部列表或日历视图展示；
- 标记原始时间、标准时间、来源邮件和确认状态；
- 用户批准、修改或拒绝建议。

验收标准：

- 创建或修改任务/日程前必须人工确认。
- 模糊时间不能直接转为已确认日程。
- 对同一邮件和同一事件重复分析时，不重复创建任务。
- MVP 不向第三方日历写入数据。

### 4.8 回复草稿、审核与发送

必须支持：

- 结合邮件、分类、抽取结果和申请上下文判断是否需要回复；
- 生成可编辑的回复正文草稿；
- 保存模型原稿和人工修改稿；
- 用户执行批准、修改后批准、拒绝或重新生成；
- 对已批准的最新草稿执行 SMTP 发送；
- 保存发送时间、结果和错误。

审核状态冻结为：

```text
PENDING
APPROVED
MODIFIED_AND_APPROVED
REJECTED
CANCELLED
EXPIRED
```

验收标准：

- 模型不能直接调用 SMTP。
- 未审核、已拒绝、已过期或旧版本草稿不能发送。
- SMTP 发送前再次校验用户、收件人、主题、草稿版本和幂等键。
- 已记录发送成功后，同一发送请求重复提交不会再次调用 SMTP。
- SMTP 连接中断导致结果无法确认时标记为 `UNKNOWN`，不得自动重试；用户核对后才能决定是否重新发送。
- Agent 只生成正文；主题、地址、称呼、签名和 MIME 由确定性 Formatter 统一组装一次。
- SMTP 失败时记录失败，不得标记为已发送，并允许用户在确认当前状态后重试。

### 4.9 求职看板与时间线

必须支持：

- 按申请阶段展示求职记录；
- 查看公司、岗位、当前确认阶段和最近事件；
- 查看由邮件产生的申请时间线；
- 从申请跳转到关联邮件；
- 展示待审核建议和近期任务。

验收标准：

- 看板只使用用户确认后的阶段，不直接使用模型建议覆盖当前阶段。
- 每次确认后的阶段变化都有来源邮件、确认时间和事件记录。
- 拒绝模型建议不会改变看板阶段。

### 4.10 低优先级邮件归档

必须支持：

- Classification Agent 输出优先级、类别和置信度；
- 用户配置低优先级归档规则和目标文件夹；
- 默认生成待审核归档任务；
- 用户明确启用规则后，允许对满足阈值的邮件自动执行；
- 保存原文件夹、执行结果和恢复依据；
- 支持提出恢复邮件动作。

验收标准：

- 自动归档规则默认关闭，默认需要确认。
- 求职相关邮件、低置信度或结果冲突时不得自动归档。
- 归档由确定性 Policy 和 IMAP Service 执行，不由 Agent 直接移动邮件。
- 不实现自动删除。
- 归档失败不会被标记为成功。

### 4.11 工作流与多智能体协作

MVP 必须体现以下独立专业能力：

- Classification Agent：求职相关性、类别、优先级和是否回复；
- Extraction Agent：公司、岗位、时间、联系人、材料等字段和证据；
- Application Agent：申请候选匹配、阶段及任务建议；
- Reply Agent：结合前序 Agent 结果生成回复草稿。

顶层工作流负责共享 State、确定性路由、结构化校验、受限重试和人工中断。MVP 不实现 LLM Supervisor 和 Review Agent。

验收标准：

- 每项专业能力具有独立的强类型输入输出。
- 能从运行记录中看到各能力的输入摘要、输出、置信度、错误和耗时。
- Pydantic Schema、状态机、证据完整性和时间歧义由确定性 Validation Node 校验。
- Agent 不直接写关键业务状态，也不直接执行 SMTP、日程或归档动作。
- 工作流暂停后可通过持久化标识恢复；重复恢复或重复审核不会重复执行外部动作。

## 5. 必须人工确认的动作

MVP 统一采用保守策略，以下操作默认需要人工确认：

- 新建求职申请；
- 修改申请阶段；
- 创建或修改任务/日程；
- 发送回复邮件；
- 多候选申请匹配；
- 模糊时间或冲突信息的最终取值；
- 确定性校验检测到事实冲突、隐私风险或低置信度结果后的处理；
- 归档和恢复邮件。

唯一例外是用户明确启用的低优先级归档规则。规则只能处理满足类别、优先级和置信度阈值的邮件，并保留撤销和审计记录。

## 6. 明确不进入 MVP 的内容

- 多个邮箱账户同时启用和并发同步；
- `Sent`、`Drafts`、垃圾箱等完整邮箱文件夹管理；
- IMAP IDLE、实时推送和大规模历史邮件导入；
- 附件内容 OCR、文档解析和模型分析；
- 第三方日历写入和双向同步；
- Google、Microsoft 等第三方 OAuth 登录，以及 Outlook/Microsoft 365 邮箱接入；
- 自动发送回复；
- 自动修改关键求职阶段；
- 自动删除邮件；
- 邮箱 Drafts 文件夹同步；
- 企业级多租户、角色权限和管理员后台；
- 移动端、小程序和桌面客户端；
- 完整招聘平台或 ATS 功能；
- 通知推送、短信和邮件提醒；
- 复杂规则编排器；
- Celery/RQ 等重型任务队列，除非实现中出现不可规避的需求；
- 大规模模型微调和向量知识库。

上述功能如果后续增加，应作为增强范围，不影响 MVP 是否通过。

## 7. 端到端验收场景

### AC-01：面试邀请完整闭环

前置条件：测试邮箱中存在一封包含公司、岗位、面试时间、地点或会议链接的邮件。

期望结果：

1. 手动同步后邮件只新增一次。
2. 邮件被分类为 `INTERVIEW`。
3. 公司、岗位和时间等字段包含原文、标准值和证据。
4. 系统提出申请匹配/新建、阶段变更和日程建议。
5. 用户确认后，看板和时间线更新。
6. 系统生成回复草稿。
7. 用户修改并批准后，SMTP 只发送一次。
8. 收件箱实际收到格式正确、没有重复称呼或落款的回复。

### AC-02：非求职邮件安全结束

前置条件：存在一封广告、订阅或普通私人邮件。

期望结果：

1. 邮件分类为 `NON_JOB`。
2. 不创建申请、阶段、任务和回复草稿。
3. 保存分类结果和处理记录后工作流结束。

### AC-03：同公司多岗位匹配冲突

前置条件：系统中存在同一公司的两个不同岗位申请，新邮件未明确岗位。

期望结果：

1. 系统返回多个候选和冲突原因。
2. 不自动关联申请，不自动修改阶段。
3. 用户选择后才建立关联并记录审核结果。

### AC-04：模糊时间

前置条件：邮件只写“下周找时间面试”或缺少年份、日期、时区。

期望结果：

1. 原始时间文本被保存。
2. 系统明确标记不确定项。
3. 不自动创建已确认日程。
4. 用户补充或修改后才保存标准时间。

### AC-05：拒信与阶段变更

前置条件：邮件明确表示招聘流程终止。

期望结果：

1. 分类为 `REJECTION`。
2. 系统提出 `REJECTED` 阶段建议并给出证据。
3. 用户拒绝建议时，看板保持原阶段。
4. 用户批准后更新阶段并写入时间线。
5. 默认不生成回复，除非 `should_reply` 明确为真并由用户触发。

### AC-06：同步与发送幂等

期望结果：

1. 同一邮箱连续同步两次，不产生重复邮件。
2. 同一邮件重复分析，不重复创建申请事件或任务。
3. 同一审核决定重复提交，只生效一次。
4. 已记录成功的发送命令重复提交时，不再次调用 SMTP；结果不明的发送不会自动重试。

### AC-07：模型或外部服务失败

期望结果：

1. 模型超时、Schema 错误、IMAP 失败和 SMTP 失败均有明确状态。
2. 失败不会被记录为成功。
3. 已成功保存的数据不会因为后续步骤失败而丢失。
4. 用户可以在修复配置或确认状态后安全重试。

### AC-08：审核暂停与恢复

期望结果：

1. 工作流在需要人工确认时持久化暂停。
2. HTTP 请求结束或服务重启后，待审核任务仍可查询。
3. 用户批准、修改或拒绝后，工作流从正确位置恢复。
4. 重复恢复不会重复执行状态更新、日程创建或邮件发送。

### AC-09：不可信 HTML 邮件

前置条件：邮件 HTML 包含脚本、事件属性、外部图片或跟踪资源。

期望结果：

1. 原始内容按受控方式保存。
2. 前端只展示安全清洗后的内容。
3. 脚本不执行，远程跟踪资源不自动加载。
4. 邮件仍能参与分类和结构化抽取。

### AC-10：低优先级邮件归档与恢复

前置条件：存在一封高置信度 `NON_JOB` 或符合用户低优先级规则的邮件。

期望结果：

1. 默认只生成归档审核任务，不直接移动邮件。
2. 用户批准或明确启用规则后，IMAP 将邮件移动到目标文件夹。
3. 系统保存原文件夹、当前文件夹和执行结果。
4. 相同归档动作重复提交不会重复执行。
5. 用户可以提出恢复动作并将邮件移回原文件夹。
6. 求职相关、低置信度或冲突邮件不会自动归档。

## 8. MVP 完成定义

只有同时满足以下条件，MVP 才能判定完成：

- AC-01 至 AC-10 均通过并保留测试证据；
- FastAPI、MySQL、LangGraph 和 Vue 形成可运行的端到端系统；
- DeepSeek 或 Qwen 至少一个模型通过统一适配层稳定运行；
- 163 测试邮箱的 IMAP 增量同步和 SMTP 发送通过；
- 核心 Pydantic Schema、状态机、去重、审核和发送幂等具有自动化测试；
- 关键日志包含 `run_id`/`thread_id`，但不泄露密钥和不必要的完整邮件正文；
- 模型建议、人工决定和最终执行结果可追踪；
- README 中提供可复现的启动、数据库迁移、测试和演示步骤；
- 已知限制和未完成增强项有明确记录。

仅有 Swagger 接口、仅有离线 Agent 演示、仅能同步邮件或仅能生成草稿，均不能视为 MVP 完成。

## 9. 冻结后的变更控制

以下变更属于范围变更，实施前必须更新本文件：

- 删除主闭环中的任一环节；
- 将人工确认改为自动执行；
- 修改顶层邮件分类、申请阶段或审核状态；
- 增加当前已批准的 163、126、QQ、Gmail、自定义 IMAP/SMTP 之外的 Provider，
  或增加外部日历、OAuth 邮箱认证和附件智能解析；
- 改变单用户 MVP 边界；
- 将某项“明确不进入 MVP”的能力调整为必做。

以下变化通常不属于业务范围变更，但需要记录架构决策：

- Agent 合并或拆分；
- checkpoint、队列和前端通信技术选择；
- ORM、测试框架和部署方式调整；
- DeepSeek 与 Qwen 主备顺序变化。
