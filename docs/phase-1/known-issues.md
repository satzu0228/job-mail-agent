# 参考项目已知问题与正式开发待修复项

本文记录第一阶段运行 Email-AI-Agent 时实际复现的问题。当前阶段以验证参考链路为主；除运行参考项目所必需的兼容修复外，下列问题留待正式系统开发时解决。

## BUG-001：邮件地址显示名解析错误

- 状态：待正式开发修复
- 触发输入：`noreply <waq0228@163.com>`
- 实际结果：称呼被解析为 `noreply <waq0228`
- 原因：`extract_name_from_email()` 使用 `split("@")` 截取字符串，未按 RFC 邮件地址格式解析显示名和地址。
- 影响：生成错误称呼，可能把尖括号或部分邮箱地址写入回复正文。
- 修复方向：使用标准库 `email.utils.parseaddr()`；优先采用合法显示名，其次使用地址本地部分，仍无法确定时进入人工编辑或使用中性称呼。
- 验收样例：纯邮箱地址、带显示名地址、中文显示名、带引号显示名、空显示名和格式异常地址。

## BUG-002：回复邮件被重复格式化

- 状态：待正式开发修复
- 实际结果：收到的邮件同时出现外层 `noreply <waq0228，您好` 和内层 `test，您好` 两个称呼。
- 原因：`response_agent` 已生成包含主题、称呼和落款的完整邮件，`send_email()` 发送前再次调用 `format_email()`。
- 影响：重复主题、称呼或落款，且第二次格式化可能截断或改变模型生成内容。
- 修复方向：明确数据契约。推荐 Agent 只返回回复正文，由确定性 Formatter 统一添加一次主题、称呼和签名；SMTP 层只负责传输，不再修改正文。
- 验收要求：预览内容与最终发出内容一致，格式化函数恰好调用一次。

## BUG-003：Human-in-the-Loop 重复询问

- 状态：待正式开发修复
- 实际结果：同一封邮件先询问中文“是否需要修改回复”，随后又询问英文“Do you want to make changes”。
- 原因：`human_review_agent` 内执行一次审核，`main.py` 在图执行结束后又执行一次审核。
- 影响：交互重复，审核状态不统一，未来接入 Web 前端后难以暂停和恢复工作流。
- 修复方向：只保留一个审核入口。正式系统应使用 LangGraph interrupt/checkpoint 或等价的持久化审核状态，由 FastAPI 提供审核接口、Vue 提供审核界面。
- 验收要求：一次草稿只生成一个待审核任务；接受、修改、拒绝均有明确状态和审计记录。

## BUG-004：Gmail 提示和“草稿”功能命名误导

- 状态：待正式开发修复
- 实际结果：使用 163 SMTP 时仍提示 `draft it to Gmail`。
- 原因：`main.py` 将 Gmail 文案硬编码；`send_draft_to_gmail()` 也并未写入 Gmail Drafts 文件夹，而是向指定 Gmail 地址发送主题带 `Draft:` 的普通邮件。
- 影响：用户误解实际动作，可能把本应保存的草稿意外发送为邮件。
- 修复方向：删除邮箱供应商硬编码；草稿应持久化到本系统数据库，或通过明确支持的邮箱 Drafts 文件夹/API 保存。任何真实发送动作必须单独确认。
- 验收要求：“保存草稿”和“发送邮件”是两个明确、不可混淆的动作。

## BUG-005：日志暴露完整邮箱地址

- 状态：待正式开发修复
- 实际结果：DEBUG/INFO 日志输出完整登录邮箱和收件人地址。
- 原因：SMTP 日志直接记录 `EMAIL_USERNAME` 和目标地址。
- 影响：开发日志、截图或论文材料可能泄露个人信息。
- 修复方向：日志默认对邮箱地址脱敏，只保留必要的域名、内部邮件 ID 和追踪 ID；禁止记录授权码、API Key 和完整正文。
- 验收要求：日志与错误报告中不出现完整凭据和不必要的个人信息。

## BUG-006：模型分类采用宽松关键词匹配

- 状态：参考运行阶段已做临时修复；正式开发需重新设计
- 实际结果：模型说明“没有 spam 特征”，原逻辑却因文本中包含 `spam` 将邮件判为垃圾邮件，导致图提前结束。
- 原因：对整段自然语言输出执行字符串包含判断。
- 影响：错误分类会跳过摘要、回复或其他关键节点。
- 正式修复方向：采用 Pydantic/JSON Schema 结构化输出、枚举校验、置信度和失败回退；低置信度进入人工审核。
- 验收要求：解释文字中出现其他类别名称时不得改变最终结构化分类。

## BUG-007：网易 IMAP/SMTP 兼容能力缺失

- 状态：参考运行阶段已做兼容修复；正式开发需抽象为邮箱适配层
- 实际结果：163 IMAP 在打开 INBOX 时返回 `Unsafe Login`；SMTP 465 无法使用原来的 STARTTLS 写法。
- 原因：原项目默认围绕 Gmail：未发送网易要求的 RFC 2971 IMAP ID，且 SMTP 固定采用 STARTTLS。
- 影响：无法直接接入 163 等使用不同安全策略的邮箱。
- 正式修复方向：按账户配置选择 IMAP ID、隐式 TLS、STARTTLS、端口和认证策略；供应商差异封装在基础设施适配层，不散落在业务逻辑中。
- 验收要求：至少对测试范围内的 Gmail/163 或其他选定邮箱执行连接、收件和发件集成测试。

## 正式开发处理优先级

| 优先级 | 问题 | 原因 |
|---|---|---|
| P0 | BUG-002 重复格式化 | 直接破坏最终发出内容 |
| P0 | BUG-003 重复审核 | 影响核心 Human-in-the-Loop 设计 |
| P0 | BUG-004 草稿/发送语义混淆 | 可能造成非预期发送 |
| P0 | BUG-006 分类解析 | 影响工作流路由正确性 |
| P1 | BUG-001 地址解析 | 影响回复称呼与隐私 |
| P1 | BUG-005 日志脱敏 | 影响个人信息安全 |
| P1 | BUG-007 邮箱适配 | 影响多邮箱兼容性 |
